1. 项目概述

Crown Rush（百关闯关）是以「投注累积经验值 → 闯关成功 → 领取奖励」为核心的长周期留存活动。活动共 100 个关卡，关卡奖励以现金为主，在 8 个里程碑关卡配置限量实体大奖。活动包含三个前台页面（活动预热页、活动进行中页、活动结束页）与一套运营后台配置能力，三页按活动状态自动切换。

项目说明
活动周期以后台配置的预热开始、活动开始、活动结束与活动下架时间为准（GMT+8）
目标用户全体已注册真实用户，支持后台配置准入条件
页面状态机pending（预热页）→ running（进行中页，到达活动开始时间自动切换）→ ended（活动结束页，到达活动结束时间自动切换）。状态以服务端时间为准，前端倒计时归零后需请求活动状态接口确认再切页
核心指标活跃留存、日均有效投注、活动参与率、实体奖品曝光转化、奖励领取率
语言当前原型三个前台页面均为中文；正式上线的前台语言（英文 / 中英双语）待运营确认，后台为中文

3. 业务规则

3.1 经验值（EXP）

  • EXP = 有效投注额 ÷ 游戏类型流水权重；老虎机 1:1、真人娱乐场 20:1、Poker 10:1、Bingo 5:1、Arcade 3:1、捕鱼 4:1（权重由后台配置）。v1.1
  • 仅统计活动周期内、参与游戏范围内的有效投注；取消注单、对冲注单不计入。
  • EXP 实时累计，用户无需报名。
  • 跨期清零：活动以自然月为一期，新活动上线时 EXP 全部清零、关卡进度不继承，下一期所有用户统一从第 1 关、0 EXP 重新开始；上一期已领取的奖励不受影响，多期活动可同时上线，上期未领取奖励在该活动被后台下架（活动下架时间到达）前均可领取。v1.1

3.2 关卡

  • 共第 1 关 - 第 100 关，每关配置 EXP 门槛与对应奖励；EXP 达标即闯关成功，关卡只进不退。v1.1
  • 可跨关闯过（单笔大额投注可一次连闯多关），跳过的关卡奖励仍可补领。

3.3 奖励

  • 现金奖励：闯关成功后需在活动页手动领取，支持「一键领取现金」批量领取全部已闯关成功的现金关卡，领取后即时存入账户余额。一键领取不包含实体奖励关卡，实体关卡必须在各自条目单独领取并完成物流校验。
  • 实体奖励：绑定 8 个里程碑关卡，每个关卡对应一件实体奖品（不附带现金）。限量发放、先到先得。当某关卡的前台剩余名额为 0 后（前台剩余名额 = 本活动该关卡分配数量 − 真实用户领取 − 机器人领取），后续闯过该关卡的用户不再展示实体奖品，该关卡自动转为「替补彩金」：卡片切换为替补彩金（普通关卡样式），文案显示「实体奖品已领完 · 改发彩金 ₱X」，领取即现金入账，且可参与「一键领取现金」。替补彩金金额由后台按关卡单独配置。
    替补彩金判断口径：以前台剩余名额为唯一口径（前台剩余名额 = 本活动该关卡分配数量 − 真实用户领取 − 机器人领取）。机器人领奖同样扣减前台剩余名额，因此可能在后台库存仍有实物时提前触发替补彩金；后台库存仅用于真实用户领取时的扣减与发货，不参与替补彩金判断。v1.1
  • 领取时限：活动结束后进入领奖缓冲期，页面自动切换为活动结束页，已闯关卡的未领取奖励不设截止时间，可随时领取；上期活动在后台手动下架前保持可领取；下架时间在创建活动时设置，可在「下架设置」中修改。v1.2
  • 提现打码要求（前台不展示）：用户领取的任何奖金（含关卡现金、替补彩金）均需完成该笔奖金 1 倍的打码量后方可提现。此规则不在预热页、进行中页及规则弹窗中展示，前台不做任何提示，由后台在钱包侧静默计算与拦截。v1.1

3.4 风控

如发现对冲、套利、同设备/同 IP 多账号等异常行为，平台有权取消参与资格并回收已发放奖励。实体大奖发放前需人工复核。

7. 运营后台需求

后台数据展示不脱敏：后台所有页面（活动、奖品、库存记录、领取记录、物流信息、数据报表及导出文件）中的用户名、手机号、收件人、收货地址等用户信息均完整显示，不做脱敏；后台访问须依赖账号权限控制与操作日志。前台闯关榜中其他玩家的用户名仍脱敏。

后台入口为「活动中心 › 流水闯关活动」，按活动配置顺序包含五个模块：奖品管理 → 活动管理 → 机器人管理 → 奖品领取记录 → 活动数据列表，进入后默认显示「活动管理」。所有金额显示千位符与 ₱ 符号；所有时间输入均使用日历卡片选择（GMT+8）。原型见《后台 · 流水闯关活动》。

公共能力说明
顶部提示栏在平台原有提示项后增加「待派发奖品：N」，N 为所有活动中状态为「待确认库存」的实体奖品记录数；点击数量跳转至「奖品领取记录」并自动筛选该状态的记录。
帮助提示操作按钮、非常见数据项及新增 / 编辑弹窗中的字段（活动状态、各时间节点、关卡数、参与游戏 / EXP 权重、物流快递预留、活动总预算、领取结果弹窗关闭秒数、单件成本、库存变动各字段、快递公司与单号、修改原因等）旁显示「?」图标，点击弹出该项的含义、计算方式或操作规则（内容见 7.9 帮助提示内容）。
操作日志启停活动、修改配置、库存变动、改奖、批量操作等均记录操作人与时间。

7.1 奖品管理

库存记录 · 操作人：每条库存记录显示操作人，按来源分三类——①「用户领奖 · 用户名」：用户领取实体奖品、生成领取记录时产生的预占；②「后台操作 · 后台用户名」：后台人员入库、报损、分配 / 释放分配、确认库存、发货出库、退货入库、成本调整等；③「系统」：系统自动处理（如超时自动释放预占）。

奖品管理不区分活动，统一管理平台实体奖品的库存；平台彩金 / 现金奖励不在此管理。活动关卡配置实体奖品时，只能从奖品管理中选择，且分配数量不得超过该奖品的可分配余量。

7.3 机器人管理

挂起与结束后的机器人：活动挂起期间机器人暂停增长，恢复后继续，挂起期间少长的部分不补；活动结束（领奖缓冲 / 已下架）后不能再新增机器人，也不能增加 EXP 或提高目标，已有机器人仍可删除。v1.2

核心逻辑：机器人通过设定经验值（EXP）实现虚拟领奖，不再按关卡比例计算机器人数量。系统按机器人 EXP 对照关卡门槛计算其闯关进度，已闯过关卡的奖励（现金 / 彩金 / 实体）自动虚拟领取。v1.1

添加：选择所属活动后，按目标关卡添加（系统自动换算该关 EXP 门槛），一次可生成 1–50 个；目标关卡可设区间，多个机器人在区间内均匀分配。昵称默认自动生成（模仿真实玩家风格、全平台不重名），也可自定义（每次 1 个，3–20 位字母、数字或下划线）。机器人昵称须做脱敏后撞名校验：按前台闯关榜脱敏规则（前 2 位 + **** + 后 3 位）处理后，不得与任一真实用户脱敏后的显示相同，也不得与真实用户名完全相同；手动填写时校验不通过则提示更换，自动生成时自动跳过冲突昵称。v1.1

成长方式：①「模仿玩家」（推荐）——拉杆范围取本活动自开始时间至当前时间，真实玩家每日 EXP 增长的最低值至最高值（以「用户 × 日」为样本统计，同时显示平均值与已进行天数），进入设置时拉杆默认停在当前单日增长的平均值；操作人员拖动拉杆或在输入框输入数值，设定该机器人未来每日增长的总 EXP（输入框可填写高于拉杆最高值的数值，按输入值计算，并提示「高于玩家单日最高值」）；系统每天按玩家活跃时段曲线把每日总 EXP 分配到 24 个小时，每小时自动增长并领取新闯过关卡的奖励，持续至活动结束，页面以 24 小时柱状图预览分配结果；一次生成多个时每个机器人在设定值 ±10% 内随机浮动，避免数据一致；不使用目标关卡（列表显示按每日增长推算的活动结束时约达关卡）；可「调整每日增长 EXP」，调整后从下一小时起按新值分配。②「逐步成长」——在 24 小时 / 3 天 / 7 天 / 活动结束前到达目标关卡，按小时均匀增加 EXP。③「立即到达」——立即闯至目标关并领取奖励。
活动初期预估：活动刚上线、尚未满 1 个完整自然日（样本不足）时，拉杆的最低值、最高值与平均值改用预估值——以平台真实玩家近 7 日日均流水（按游戏分类）× 本活动各游戏分类的「流水金额 : EXP」换算比例，得出每位玩家的预估单日 EXP 增长，再取最低、最高与平均；页面标注「预估值」。满 1 个完整自然日后自动切换为本活动实际数据，标注「实际值」。v1.1

管理：列表展示成长进度、目标关卡、成长计划、状态（成长中 / 已达成 / 已暂停）、已领奖励、闯关榜名次；支持单个或勾选批量「提高目标 / 暂停 / 恢复 / 删除」。顶部汇总：机器人总数、成长中、已达成、已领实体奖品、闯关榜 TOP 100 内人数。v1.1

约束：EXP 只增不减（目标关卡只能提高）；删除后已领奖励、占用名额与闯关榜记录不回退；删除后该机器人保留在闯关榜中，榜单数据冻结在删除时刻（已领取金额、已领实体件数、最后领取时间不再变化），之后按排行榜规则正常排序，可被其他用户或机器人超越而下移，直至移出 TOP 100。v1.1

领奖影响：机器人领奖不产生领取记录、不发货、无需人工处理；实体奖品减少前台剩余数量（与真实用户领取表现一致），不扣后台库存；后台奖品表格分别统计真实用户领取与机器人领取数量。v1.1

闯关榜：闯关榜是领取用户的排行榜，机器人参与领奖，因此以真人形式参与排名——按已领取奖励与真实用户一起排序，前台按普通玩家展示（用户名同样脱敏，不显示机器人标识）；剔除风控账号。v1.1

数据：机器人数据带机器人标识，成本、预算使用率、获客成本、领取人数等真实指标全部排除机器人数据。v1.1

9. 接口与异常

  • 核心接口：活动信息、用户进度、关卡任务列表、领取（单项/一键）、领奖记录、排行榜、物流信息提交与查询、验证码发送与校验。
  • 领取接口需幂等，防止重复领取；实体奖品领取需库存原子扣减。
  • 异常态：未登录、活动未开始/已结束、库存售罄、领取失败、网络异常，均需前端明确提示文案。
  • 活动状态接口：返回 status（pending / running / ended）、server_ts、本期起止时间与下一期信息。前端在倒计时归零、页面进入前台、以及每 60 秒轮询时调用；切页一律以该接口为准，不得仅依赖本地倒计时。
  • 结束态接口差异：进度接口在 ended 状态下返回封存后的最终 EXP 与最终关卡（不再随投注变化）；关卡任务接口仅返回已闯过的关卡；实体奖品接口仅返回用户已闯过的奖品关卡；榜单接口返回封存的最终排名。
  • ended 状态下仍需支持：单项领取、一键领取现金、物流信息提交 / 查询 / 修改、短信验证码、领奖记录查询。

11. 各角色协作 Tips

以下为结合本项目特点（长周期、强奖励、限量实体奖品、多弹窗流程、菲律宾本地市场）给各角色的实操建议，非硬性需求，但能显著减少返工与线上风险。

UI / 视觉设计
  • 先定关卡卡片的状态矩阵：未闯关 / 可领取 / 已领取 / 实体关卡 / 实体售罄替补彩金，共 5 种，一次出全比事后补状态省时。v1.1
  • 进度条内文字必须与填充色互补：本项目踩过「绿字压绿条」的坑，凡是条内标签都要同时校验 0% 与 100% 两个极端的对比度（≥4.5:1）。
  • 节日素材统一走透明底 PNG：奖品图、主视觉、装饰件都需抠底并裁至主体，切图前先确认最终渲染尺寸，按 2-3 倍导出即可，避免上传 1700px 原图导致弹窗白屏。
  • 弹窗按「高度预算」设计：主视觉 + 金额 + 列表 + 按钮的总高必须在 75-90% 视口内闭合，列表条数用固定值（如 5 条）而非「自适应」，否则小屏必然挤掉按钮。
  • 为空态与售罄态出图：「暂无可领取的现金奖励」「已领完」「未登录」这三种状态最容易被漏掉，却是用户高频看到的界面。
前端开发
  • 活动状态一律以服务端为准：倒计时仅用于展示，归零后必须请求活动状态接口再切页，防止本地改时间提前进入。
  • 领取按钮做防抖 + 幂等：一键领取与单关领取都要禁用二次点击并携带 order_id，网络重试不能造成重复入账。
  • 弹窗层级与滚动隔离：物流填写 → 二次确认 → 短信验证三层弹窗会叠加，需统一 z-index 规范并锁定背景滚动。
  • 列表滚动定位用 scrollTo 而非 scrollIntoView：容器内定位到「首个未领取关卡」时，scrollIntoView 会带动整页跳动。
  • 装饰动效走 transform / opacity：动效都用 GPU 属性，避免 top/left 动画在中低端安卓机上掉帧。
  • 图片资源按渲染尺寸出：弹窗内 70px 高的图不要引用 560px 以上的源图，首屏与弹窗素材建议预加载。
  • 打码规则相关字段绝不接入前端：接口若返回也需忽略，避免被抓包反推规则。
后端开发
  • 库存扣减必须走分布式锁或数据库行锁：8 个里程碑关卡是典型秒杀场景，先锁定名额再生成工单，超时未完成则释放。
  • EXP 计算与注单结算解耦：用消息队列消费注单，支持重放与补算；取消注单、对冲注单需可回退 EXP。
  • 关卡只升不降：EXP 回退时保留已达成关卡与已领奖励，避免用户资产被回收引发客诉。
  • 替补彩金金额与打码倍数做配置化：不要写死在代码里，运营需要在活动中期调整。v1.1
  • 物流信息修改留全量日志：时间、修改前后值、IP、设备、验证码校验记录，便于风控与客服追溯。
  • 验证码接口做频率与次数限制：同手机号 60 秒一次、单日上限、连续失败锁定，防短信轰炸与撞库。
  • 榜单用缓存 + 定时计算：TOP 100 每小时刷新即可，不要实时查库；同时为「我的排名」单独提供轻量接口。
测试
  • 时间类用例优先：活动开始前 1 分钟 / 归零瞬间 / 活动结束瞬间、跨时区、本地时间被改早或改晚，共 6 组必测。
  • 库存并发场景：多人同时领取最后一件实体奖品，验证只有一人成功、其余改发替补彩金且金额正确。v1.1
  • 领取幂等：断网重连、重复点击、接口超时重试后核对钱包流水笔数与金额。
  • 物流三层弹窗全路径：未登录点击领取、填写中放弃、二次确认取消、验证码错误/过期/重发、绑定后再次进入应变为「查看物流信息」。
  • 替补彩金回归：把某关卡库存设为 0，验证列表卡片样式、文案、按钮行为、一键领取是否纳入、榜单实物列是否剔除。v1.1
  • 小屏与长文本：360×640 等小屏下弹窗按钮是否可见可点；超长用户名、超大金额（7 位数）是否截断错位。
  • 三态自动切页：预热→进行中（活动开始时间）、进行中→结束（活动结束时间）两个切换点；本地时间改早/改晚均应由服务端状态纠正。
  • 结束页专项：未解锁关卡不显示、EXP 停止累计、库存卡组与叠卡仅含已闯关卡、结束态仍可完成领取与物流全流程。
  • 埋点校验：按 8.3 清单逐事件核对参数完整性，重点验证服务端上报事件与前端事件不重复计数。
运维 / 运营支持
  • 活动首日与整点做扩容预案：0 点开赛、每小时榜单刷新、发薪日是三个流量尖峰，提前评估数据库与缓存容量。
  • 关键告警阈值：领取失败率 >1%、库存接口响应 >500ms、短信发送成功率 <95%、钱包入账延迟 >10s，均需即时告警。
  • 准备非核心模块一键关闭开关：榜单、热门推荐、热门活动等非核心模块可独立关闭，保障领取主链路。v1.1
  • 奖励发放对账每日跑批：活动侧领取记录与钱包流水按 order_id 双向核对，差异当日处理。
  • 实体奖品库存预警：剩余 ≤20% 时通知运营，提前决定补货或启用替补彩金。v1.1
  • 上线前演练回滚：活动配置、关卡奖励表支持快速回滚到上一版本；保留活动暂停能力（暂停后 EXP 继续累计但停止领取）。
  • 客服话术与后台权限先就位：物流修改、补发、异常领取三类工单的处理流程与权限边界在开赛前确认。
