1. 项目概述

Crown Rush（百关闯关）是以「投注累积经验值 → 闯关成功 → 领取奖励」为核心的长周期留存活动。活动共 100 个关卡，关卡奖励以现金为主，在 8 个里程碑关卡配置限量实体大奖。活动包含三个前台页面（活动预热页、活动进行中页、活动结束页）与一套运营后台配置能力，三页按活动状态自动切换。

项目说明
活动周期以自然月为一期，示例期 12/01 00:00:00 - 12/31 23:59:59（GMT+8）
目标用户全体已注册真实用户，支持后台配置准入条件
页面状态机pending（预热页）→ running（进行中页，12/01 00:00:00 自动切换）→ ended（活动结束页，12/31 23:59:59 自动切换）。状态以服务端时间为准，前端倒计时归零后需请求活动状态接口确认再切页
核心指标活跃留存、日均有效投注、活动参与率、实体奖品曝光转化、奖励领取率
语言当前原型三个前台页面均为中文；正式上线的前台语言（英文 / 中英双语）待运营确认，后台为中文

2.3 物流信息修改流程

用户点击「修改地址」 → 系统向账号绑定手机号发送短信验证码 → 用户输入验证码校验通过 → 前台开放编辑表单 → 用户自行修改并保存 → 系统记录修改日志（时间 / 修改前后值 / 设备） → 前台展示更新后的物流信息。奖品已进入发货流程时地址冻结，此时才需联系客服。

2.4 系统时序（后端视角）

触发执行方动作

EXP 变更活动服务比对关卡门槛 → 闯关成功 → 生成可领取奖励记录

每小时定时排行榜任务重算 TOP 100 并写入缓存，剔除风控标记账号

新一期开启活动服务归档上期数据 → EXP 与关卡进度全量清零 → 上期未领取奖励失效 → 所有用户从第 1 关 0 EXP 重新开始

3. 业务规则

3.1 经验值（EXP）

  • EXP = 有效投注额 ÷ 游戏类型流水权重；老虎机 1:1，真人娱乐场 20:1（权重由后台配置）。
  • 仅统计活动周期内、参与游戏范围内的有效投注；取消注单、对冲注单不计入。
  • EXP 实时累计，用户无需报名。
  • 跨期清零：活动以自然月为一期，新一期开启时 EXP 全部清零、关卡进度不继承，下一期所有用户统一从第 1 关、0 EXP 重新开始；上一期已领取的奖励不受影响，未领取的奖励在新一期开启时失效（活动结束至新一期开启之间为领奖缓冲期，可随时领取）。

3.2 关卡

  • 共第 1 关 - 第 100 关，每关配置累计投注门槛与对应奖励；EXP 达标即闯关成功，关卡只进不退。
  • 可跨关闯过（单笔大额投注可一次连闯多关），跳过的关卡奖励仍可补领。

3.3 奖励

  • 现金奖励：闯关成功后需在活动页手动领取，支持「一键领取现金」批量领取全部已闯关成功的现金关卡，领取后即时存入账户余额。一键领取不包含实体奖励关卡，实体关卡必须在各自条目单独领取并完成物流校验。
  • 实体奖励：绑定 8 个里程碑关卡，每个关卡对应一件实体奖品（不附带现金）。限量发放、先到先得。当某关卡的实体奖品库存领完后，后续闯过该关卡的用户不再展示实体奖品，该关卡自动转为「彩金奖励」：卡片降级为普通关卡样式，文案显示「实体奖品已领完 · 改发彩金 ₱X」，领取即现金入账，且可参与「一键领取现金」。彩金替代金额由后台按关卡单独配置。
  • 领取时限：活动结束后进入领奖缓冲期，页面自动切换为活动结束页，已闯关卡的未领取奖励不设截止时间，可随时领取；新一期开启时上期未领取的奖励失效（届时如需设定明确截止日，由后台配置并在结束页统一展示）。
  • 提现打码要求（前台不展示）：用户领取的任何奖金（含关卡现金、彩金替代）均需完成该笔奖金 1 倍的打码量后方可提现。此规则不在预热页、进行中页及规则弹窗中展示，前台不做任何提示，由后台在钱包侧静默计算与拦截。

3.4 风控

如发现对冲、套利、同设备/同 IP 多账号等异常行为，平台有权取消参与资格并回收已发放奖励。实体大奖发放前需人工复核。

4. 前台页面一：活动预热页

活动开始前展示，目标是制造期待、引导用户提前熟悉规则与参与方式。预热页倒计时结束（12/01 00:00 GMT+8）后，落地页自动切换显示为「活动进行中页」：前端倒计时归零即请求活动状态接口，服务端返回 running 后无刷新替换页面内容；若用户此时正停留在页面上，同样即时切换。活动状态一律以服务端时间为准。

开赛提示文案说明：活动开始即可累计 EXP 闯关并领取奖励；越早参与越早解锁限量实体奖品，领完即止（不含预约功能）

5.1 物流信息流程

领取实体奖品时的判定：点击实体奖品「领取」→ 系统判断该账号是否已绑定物流信息。未绑定 → 弹出物流信息填写弹窗，完成填写后进入二次确认；已绑定 → 直接进入二次确认弹窗，展示当前物流信息，用户确认后才真正领取并生成发货工单。二次确认弹窗内提供「修改地址」入口，用户点击后需通过账号手机号短信验证码校验，验证通过即可自行修改并保存，无需联系客服。

  1. 用户点击「填写物流信息」；未登录则跳转登录页，登录后返回继续填写。
  2. 弹窗中展示当前账号用户名（不可修改），提示「该物流信息将绑定此账号」。
  3. 提交后物流信息绑定账号；页面入口变为「查看物流信息」，修改需经短信验证码校验。
  4. 如需修改，用户点击「修改地址」，系统向账号绑定手机号发送短信验证码；校验通过后用户可在页面内自行编辑并保存，系统记录修改日志（时间、修改前后值、IP/设备）。

5.2 一键领取结果弹窗

点击「一键领取现金」成功后以弹窗反馈结果，不使用 toast 提示。弹窗为圣诞节日风格：矩形卡片为主体，顶部积雪铃铛花环与木牌为突破矩形边界的装饰层，木牌上显示「MALIGAYANG PASKO」问候语（菲律宾本地化），卡内飘雪与金色星点为氛围动效。

区块要求
领取成功区「CLAIM SUCCESSFUL / REWARD CREDITED」主视觉图（透明底、带弹入动效）+ 金框金额面板：本次领取项数、到账总金额、「✓ 已存入账户余额」标识
领取明细独立面板，标题行显示「N 项 · 实体奖品需单独领取」；固定 5 条高度，超出可滚动；每行为「第 X 关 — 现金 ₱Y」
关闭机制30 秒倒计时自动关闭；倒计时以「驯鹿拉雪橇沿雪道驶向圣诞树」的进度条呈现（雪橇后有扬雪粒子特效），秒数同时显示在确认按钮标签上（「N s 后关闭」）；用户亦可点击「知道了」立即关闭
尺寸约束宽度固定（约 318px），高度自适应内容并受视口上限约束；顶部预留装饰溢出空间，矮屏下确认按钮与倒计时须始终可见可点击

5.3 实体奖品库存耗尽的降级规则

当某实体关卡库存归零后，后续闯过该关卡的用户不再展示实体奖品：该关卡在列表中降级为普通关卡样式，文案显示「实体奖品已领完 · 改发彩金 ₱X」，可直接领取现金并纳入「一键领取现金」批量领取范围。彩金替代金额由后台按关卡单独配置。闯关榜的实体奖品列同样不再计入该关卡。

项目规则
触发条件该实体关卡实时库存 = 0（含已锁定待发货的名额）时，对尚未完成领取的用户生效；已完成领取的用户不受影响
前台表现卡片降级为普通关卡样式，文案「实体奖品已领完 · 改发彩金 ₱X」，按钮为普通「领取」，不再进入物流信息流程
发放方式领取后彩金即时存入账户余额，可参与「一键领取现金」批量领取
打码要求该笔彩金同样需完成1 倍打码量后方可提现，与关卡现金奖励口径一致；前台不展示、不提示，由钱包侧静默计算与拦截（详见 3.3）
记录领奖记录中记为现金奖励，备注来源为「第 X 关实体奖品彩金替代」，供客服与风控追溯

6. 前台页面三：活动结束页（领奖缓冲）

页面切换：活动结束时间（12/31 23:59:59 GMT+8）到达后，进行中页自动切换为活动结束页——前端倒计时归零即请求活动状态接口，服务端返回 ended 后跳转；用户此时若停留在页面上同样即时切换。状态一律以服务端时间为准，防止本地时间被篡改。

页面目标：为已参与但尚未领奖的用户提供领奖通道。当前无领奖截止时间限制，页面不展示任何截止倒计时或失效提示；如后续需要设定截止，由后台配置并在该页统一展示。

模块与进行中页的差异
顶部与状态条状态标识改为「已结束」；状态条显示「本期活动已结束 · 奖励可继续领取」，并以静态提示条说明「奖励领取窗口开放中 / 未领取的奖励可随时领取」；移除结束倒计时与本期进度
我的成绩徽章显示最终关卡；EXP 条改为「本期累计 EXP · 已停止累计」（满格、不再显示还需 EXP）；新增「待领取奖励 N 项 · ₱X」与「已领取 N 项」汇总
EXP 累计停止累计：活动结束后的投注不再产生 EXP，关卡不再推进
关卡列表仅显示已闯过的关卡，未解锁关卡不再渲染；列表上方标注「本期已闯关卡 · 共 N 关 / 未解锁关卡不再显示」；状态仅有 领取 / 已领取；无可领时按钮为「奖励已全部领取完毕」
实体奖品库存卡组与奖品叠卡均仅展示用户已闯过的实体奖品关卡；领取、物流信息、二次确认、短信验证改址等流程完整保留

8. 数据埋点需求

8.1 分析目标

  • 拉新与触达：预热期各渠道进入量、预热页到活动页的承接率。
  • 激活转化：浏览 → 首次投注（首次获得 EXP）→ 首次闯关成功 → 首次领取的漏斗转化。
  • 留存与深度：日活跃参与人数、人均闯关数、关卡分布与卡点（哪一关流失最多）。
  • 奖励效率：现金派出总额、实体奖品消耗速度与剩余预估、彩金替代占比、ROI（活动期投注增量 ÷ 奖励成本）。
  • 体验阻塞：领取失败率、物流信息填写与验证码流程的流失点、未登录点击领取的比例。
  • 导流效果：热门推荐 / 先行热身 / 热门活动各位置的点击与后续投注贡献。

8.5 埋点实施要求

  • 金额与奖励发放类事件以服务端上报为准（cr_stage_up、cr_claim_result、cr_fallback_cash），前端事件仅用于行为分析，避免刷单与重复计数。
  • 所有领取类事件携带 order_id 做幂等去重，与钱包流水可对账。
  • 曝光事件做节流：同一模块同一次页面会话内只上报一次，滑动类事件合并上报间隔 ≥500ms。
  • 未登录用户以设备 ID 归因，登录后需回溯绑定 user_id，保证漏斗可串联。
  • 打码量规则相关的任何字段与提示均不得下发至前端，仅在服务端与看板内部使用。
  • 事件命名统一前缀 cr_，上线前需与数据团队确认埋点文档版本与测试环境校验通过。

9. 接口与异常

  • 核心接口：活动信息、用户进度、关卡任务列表、领取（单项/一键）、领奖记录、排行榜、物流信息提交与查询、验证码发送与校验。
  • 领取接口需幂等，防止重复领取；实体奖品领取需库存原子扣减。
  • 异常态：未登录、活动未开始/已结束、库存售罄、领取失败、网络异常，均需前端明确提示文案。
  • 活动状态接口：返回 status（pending / running / ended）、server_ts、本期起止时间与下一期信息。前端在倒计时归零、页面进入前台、以及每 60 秒轮询时调用；切页一律以该接口为准，不得仅依赖本地倒计时。
  • 结束态接口差异：进度接口在 ended 状态下返回封存后的最终 EXP 与最终关卡（不再随投注变化）；关卡任务接口仅返回已闯过的关卡；实体奖品接口仅返回用户已闯过的奖品关卡；榜单接口返回封存的最终排名。
  • ended 状态下仍需支持：单项领取、一键领取现金、物流信息提交 / 查询 / 修改、短信验证码、领奖记录查询。

11. 各角色协作 Tips

以下为结合本项目特点（长周期、强奖励、限量实体奖品、多弹窗流程、菲律宾本地市场）给各角色的实操建议，非硬性需求，但能显著减少返工与线上风险。

UI / 视觉设计
  • 先定关卡卡片的状态矩阵：未闯关 / 可领取 / 已领取 / 实体关卡 / 实体售罄降级，共 5 种，一次出全比事后补状态省时。
  • 进度条内文字必须与填充色互补：本项目踩过「绿字压绿条」的坑，凡是条内标签都要同时校验 0% 与 100% 两个极端的对比度（≥4.5:1）。
  • 节日素材统一走透明底 PNG：奖品图、主视觉、装饰件都需抠底并裁至主体，切图前先确认最终渲染尺寸，按 2-3 倍导出即可，避免上传 1700px 原图导致弹窗白屏。
  • 弹窗按「高度预算」设计：主视觉 + 金额 + 列表 + 按钮的总高必须在 75-90% 视口内闭合，列表条数用固定值（如 5 条）而非「自适应」，否则小屏必然挤掉按钮。
  • 菲律宾本地化元素要真实而非符号化：Parol 星灯、Maligayang Pasko 问候、₱ 货币符号优于泛化的圣诞树图标；同时避免过度装饰压住核心信息。
  • 为空态与售罄态出图：「暂无可领取的现金奖励」「已领完」「未登录」这三种状态最容易被漏掉，却是用户高频看到的界面。
前端开发
  • 活动状态一律以服务端为准：倒计时仅用于展示，归零后必须请求活动状态接口再切页，防止本地改时间提前进入。
  • 领取按钮做防抖 + 幂等：一键领取与单关领取都要禁用二次点击并携带 order_id，网络重试不能造成重复入账。
  • 弹窗层级与滚动隔离：物流填写 → 二次确认 → 短信验证三层弹窗会叠加，需统一 z-index 规范并锁定背景滚动。
  • 列表滚动定位用 scrollTo 而非 scrollIntoView：容器内定位到「首个未领取关卡」时，scrollIntoView 会带动整页跳动。
  • 装饰动效走 transform / opacity：飘雪、雪橇、脉冲都用 GPU 属性，避免 top/left 动画在中低端安卓机上掉帧。
  • 图片资源按渲染尺寸出：弹窗内 70px 高的图不要引用 560px 以上的源图，首屏与弹窗素材建议预加载。
  • 打码规则相关字段绝不接入前端：接口若返回也需忽略，避免被抓包反推规则。
后端开发
  • 库存扣减必须走分布式锁或数据库行锁：8 个里程碑关卡是典型秒杀场景，先锁定名额再生成工单，超时未完成则释放。
  • EXP 计算与注单结算解耦：用消息队列消费注单，支持重放与补算；取消注单、对冲注单需可回退 EXP。
  • 关卡只升不降：EXP 回退时保留已达成关卡与已领奖励，避免用户资产被回收引发客诉。
  • 彩金替代金额与打码倍数做配置化：不要写死在代码里，运营需要在活动中期调整。
  • 物流信息修改留全量日志：时间、修改前后值、IP、设备、验证码校验记录，便于风控与客服追溯。
  • 验证码接口做频率与次数限制：同手机号 60 秒一次、单日上限、连续失败锁定，防短信轰炸与撞库。
  • 榜单用缓存 + 定时计算：TOP 100 每小时刷新即可，不要实时查库；同时为「我的排名」单独提供轻量接口。
测试
  • 时间类用例优先：活动开始前 1 分钟 / 归零瞬间 / 活动结束瞬间、跨时区、本地时间被改早或改晚，共 6 组必测。
  • 库存并发场景：多人同时领取最后一件实体奖品，验证只有一人成功、其余降级为彩金且金额正确。
  • 领取幂等：断网重连、重复点击、接口超时重试后核对钱包流水笔数与金额。
  • 物流三层弹窗全路径：未登录点击领取、填写中放弃、二次确认取消、验证码错误/过期/重发、绑定后再次进入应变为「查看物流信息」。
  • 降级态回归：把某关卡库存设为 0，验证列表卡片样式、文案、按钮行为、一键领取是否纳入、榜单实物列是否剔除。
  • 小屏与长文本：360×640 等小屏下弹窗按钮是否可见可点；超长用户名、超大金额（7 位数）是否截断错位。
  • 三态自动切页：预热→进行中（12/01 00:00:00）、进行中→结束（12/31 23:59:59）两个切换点；本地时间改早/改晚均应由服务端状态纠正。
  • 结束页专项：未解锁关卡不显示、EXP 停止累计、库存卡组与叠卡仅含已闯关卡、结束态仍可完成领取与物流全流程。
  • 埋点校验：按 8.3 清单逐事件核对参数完整性，重点验证服务端上报事件与前端事件不重复计数。
运维 / 运营支持
  • 活动首日与整点做扩容预案：0 点开赛、每小时榜单刷新、发薪日是三个流量尖峰，提前评估数据库与缓存容量。
  • 关键告警阈值：领取失败率 >1%、库存接口响应 >500ms、短信发送成功率 <95%、钱包入账延迟 >10s，均需即时告警。
  • 准备一键降级开关：榜单、热门推荐、热门活动等非核心模块可独立关闭，保障领取主链路。
  • 奖励发放对账每日跑批：活动侧领取记录与钱包流水按 order_id 双向核对，差异当日处理。
  • 实体奖品库存预警：剩余 ≤20% 时通知运营，提前决定补货或启用彩金替代。
  • 上线前演练回滚：活动配置、关卡奖励表支持快速回滚到上一版本；保留活动暂停能力（暂停后 EXP 继续累计但停止领取）。
  • 客服话术与后台权限先就位：物流修改、补发、异常领取三类工单的处理流程与权限边界在开赛前确认。
